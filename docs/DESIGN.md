# agent-box design (v2: Incus-native)

On-demand compute for coding agents on Tyler's Windows gaming PC (`desktop-l0rvq1v`: Ryzen 5 3600 6c/12t, 32 GB, RTX 3070).
**Never wipe, repartition or dual-boot the PC.** Everything runs on top of Windows.
**Reuse, don't rebuild:** Incus provides the API, auth, dashboard and box lifecycle. We write only glue.

## Goals

1. Agents on the laptop can get disposable Linux boxes.
2. Agents can offload heavy test runs from a laptop git worktree (Go `-race`, vitest, Android unit tests).
3. Tyler picks how much of the PC agents get (My PC / Shared / Full) with one click.

## What we use as is

| Need | Existing tool |
|---|---|
| Linux host on Windows | WSL2 distro `agents` (Ubuntu 24.04, systemd on, automount + interop off, VHDX on the biggest drive, `sparseVhd`) |
| Boxes, API, auth | **Incus** from the Zabbly repo (Ubuntu's 6.0.0 has nested AppArmor issues), HTTPS API on `:8443` |
| Network reach | Tailscale **inside** the distro as node `agent-box`; WSL stays on NAT networking |

| Dashboard | Incus web UI (`incus-ui-canonical`) at `https://agent-box.<tailnet>.ts.net:8443`, with a Let's Encrypt certificate from Tailscale (`provision/https-cert.sh`, renewed weekly) |
| Client on the laptop | Windows `incus` client (`winget install LinuxContainers.Incus`), `incus remote add pc` |
| Image | `images:ubuntu/24.04/cloud` + cloud-init in the `agents` profile (git, build-essential, Go, Node LTS, uv, JDK 17, lazy Android SDK hook, gh, Chromium's libraries), published once as `agent-base` |
| Caches | Custom storage volume `cache` mounted at `/cache` (Go, npm, Gradle, Android SDK, Robolectric, uv caches; Puppeteer and Playwright browsers) |

The `agents` project's `default` profile sets `security.nesting=true`, the cache volume, cloud-init and medium-size limits for boxes launched without `box`. The Linux kernel must be 6.12+ for Incus 7.x, which documents it as its minimum (7.0 raised it from 5.15 and dropped cgroup v1); `setup-host.sh` checks on every host, and `install-pc.ps1` runs `wsl --update`.

## Isolation

Project `agents` has its own profiles (`features.profiles=true`): Incus refuses `restricted=true` on a project without them. Agents' certs can edit those profiles, but `restricted=true` still validates what goes in them, the project caps bound the totals, and the tray resets each box's own CPU limits every tick. `features.images=false` shares images. Neither can change after creation, so `setup-host.sh` only checks an existing project and says how to recreate it if they are wrong. The project is `restricted=true` with `restricted.containers.privilege=unprivileged`, `restricted.containers.nesting=allow`, `restricted.devices.nic=managed` (`incusbr0`), and, on WSL only, for the GPU box, `restricted.devices.disk=allow` with `restricted.devices.disk.paths=/usr/lib/wsl/lib,/usr/lib/wsl/drivers` and `restricted.devices.unix-char=allow` (elsewhere `managed` and `block`). Project caps on the PC: `limits.instances=10`, `limits.cpu=24` and `limits.disk=210GiB`, set by `setup-host.sh`, and `limits.memory`, which the tray sets by mode (see Memory). On a Linux server with no tray, `setup-host.sh` sizes them from the machine (`provision/README.md`), sets `limits.memory` once, and the mode stays Shared. They are allocation caps, not usage caps. Incus refuses to lower one below what existing instances (stopped ones too) already hold.

What the GPU keys open up (checked in the Incus reference and source on 2026-11-24):

- **Disks.** Pool volumes (root, `cache`) pass as they did under `managed`. A host-path disk is allowed only if its `source` is inside one of the two WSL folders, matched on whole path components and opened with `openat2`, so a symlink can't lead outside them; `shift=true` is refused. No key enforces `readonly=true`, but boxes are unprivileged and those files belong to host root, so a box can read them and not write them. They are NVIDIA's user-space libraries (libcuda, libnvidia-ml, nvidia-smi) and the driver files Windows' driver store gives WSL: nothing about Tyler or his files.
- **Character devices.** Incus has no per-path key: `unix-char` is allow or block for every character device. So an agent's cert can attach `/dev/dxg` to any box, not only a GPU box, and can attach other host character devices too (`/dev/kmsg`, `/dev/net/tun`, ...). The box stays unprivileged, so devices that need host capabilities (`/dev/mem`, device-mapper control) still refuse it. Attaching `/dev/dxg` by hand bypasses the one-GPU-box rule and the tray's stop in My PC, because the tray finds GPU boxes by `user.box.size=gpu`. We accept that: agents use `box`, which never does it. A narrower setup, if it is ever needed, is a second project for the GPU box with `limits.instances=1`.

A restricted cert can still resume an instance and edit its own `limits.cpu`. So the modes are enforced by the tray's admin cert on every tick, not by permissions (see the tray below).

## Box sizes

The table lives in `internal/mode/size.go`; `box`, the tray and `box help` read it there.

| size | CPUs Shared / Full | RAM | root disk |
|---|---|---|---|
| small | 1 / 2 | 2GiB | 18GiB |
| medium (default) | 2 / 4 | 4GiB | 30GiB |
| large | 4 / 8 | 8GiB | 40GiB |
| gpu | 4 / 6 | 8GiB | 40GiB, plus the RTX 3070 |

- `box` launches every box with `user.box.size`, `limits.memory`, a root disk `size` and the Shared `limits.cpu` on the instance, so no extra profiles are needed. A box without the key (one launched before sizes, or by hand) is medium. Boxes are never resized: memory and disk are fixed at launch.
- The tray sets each box's `limits.cpu` from its size and the mode on every tick. An agent could rewrite `user.box.size` on its own box to get more CPUs; memory stays as launched, and the project caps still bound the total.
- Incus counts configured allocations for all boxes, including stopped boxes. With Full's 24GiB of RAM the project fits ten small boxes (the instance cap; memory would allow twelve), six medium, or three large; with 12GiB, half that. The 24-CPU cap leaves room for those mixes in Full mode. Small boxes allocate the most disk per GiB of RAM, so ten small root disks plus the 30GiB cache (210GiB) is the most the caps allow, and `limits.disk` is 210GiB.
- The disk cap is above the btrfs pool's 200GiB on purpose (2026-11-24). Both are allocations, and real use was 3.5GiB: boxes are clones of `agent-base` and write little. What really bounds the disk is the free space on C:, where the distro's sparse VHDX lives (190GB free that day); a pool that grows past that fills C: first, so a bigger pool would buy nothing.
- `box status` works out what fits now from the caps minus the existing boxes' Full CPUs, memory and count, and the disk Incus reports in `incus project info`. A size fits if it fits as things are, or once reclaimable GPU boxes (below) are deleted; in that case the memory cap is the one the tray will set for the boxes left, max(the mode's budget, what they hold), not today's. A `box run` that Incus refuses for project limits waits in the PC's queue, like one in My PC ([queue.md](queue.md)); `--no-queue` and `box new` exit 75.

### The GPU box

The PC's RTX 3070 (8GB of VRAM) is a size, `gpu`, so agents ask for it with `box run --gpu` (or `--size gpu`; MCP `gpu: true`). WSL2 exposes the GPU as `/dev/dxg` plus two host folders, and these three devices made `nvidia-smi` and the CUDA driver API work in an unprivileged box built from `agent-base` (proven by hand on 2026-11-24):

- `dxg`: `unix-char`, `path=/dev/dxg`, `mode=0666`
- `wsllib`: `disk`, `/usr/lib/wsl/lib` read-only (libcuda, libnvidia-ml and `nvidia-smi`)
- `wsldrivers`: `disk`, `/usr/lib/wsl/drivers` read-only (Windows' driver store; without it nvidia-smi can't reach the driver)

plus `environment.LD_LIBRARY_PATH=/usr/lib/wsl/lib` and an `environment.PATH` that ends in that folder, so `nvidia-smi` runs by name. `box` adds them at launch (the devices as YAML on `incus launch`'s stdin, since `-d` only overrides devices a profile has). The tables are `GPUDevices` and `GPUEnv` in `internal/mode/size.go`.

- **Throwaway only.** A GPU run always gets a throwaway box, never the repo's reused box, so an idle box doesn't hold the GPU. `box new --gpu` makes a named one for whoever asks; `box run --gpu --box <it>` uses it.
- **One at a time.** Before launching, `box` looks for another instance with `user.box.size=gpu` that is running or frozen. If one exists the run waits in the queue; with `--no-queue` it exits 75 with `the GPU box is in use (job X); run on CPU or wait`. Throwaway GPU boxes that are done are deleted on the way, since they would hold 8GiB of the memory cap: stopped ones the tray marked, and ones more than 15 minutes old that are stopped or run no job. A younger box may be one another run is starting (Incus creates it stopped, and it runs no job until its PID file is written), so it counts as in use. Two launches racing past that check are caught right after launch: a run that finds another GPU box (running, paused, or still being created) deletes its own and waits in the queue (`--no-queue`: exit 75), as does a run whose own box is gone, so both may back off, but the GPU never has two boxes.
- **VRAM comes back in My PC.** A frozen CUDA process keeps its GPU memory, so pausing a GPU box would leave the owner short of VRAM. In My PC the tray **stops** a GPU box (`incus stop --force`) instead of pausing it. First it marks it with `user.box.stopped=mypc`; once the stop worked it shortens `user.expires` to 30 minutes from now (not before, or a box whose stop failed and that later resumed would be reaped mid-job), so the reaper removes the dead box soon but `box job` can still explain it and `box pull` can fetch partial output. Until then it still holds a GPU box's memory and disk against the caps, so `box status` doesn't count it, and any launch the caps refuse deletes it and tries once more (found live on 2026-11-24, when a stopped GPU box left no room for a CPU box). If the stop fails it pauses the box and retries the stop next tick. A stopped GPU box stays stopped when the mode comes back. The job is lost: `box job` exits 75 with `the GPU box was stopped because the PC's owner switched it to My PC; rerun later or on CPU`.
- `box status` has one `gpu` field and line: `free`, `free, but no room for a gpu box now`, `in use: job X`, or `unavailable: the PC is in My PC mode`. The gpu size is left out of the `room for` advice.

## Glue we write

### 1. `box` (Go, one binary, laptop): CLI + stdio MCP server, shaped like Murmur
It shells out to the `incus` CLI, using the `pc` remote and the `agents` project. Each command is also an MCP tool with the same behaviour.

```
box status                       # box_status: advice line, reachability, mode, free slots, room per size, this repo's box (and size) and running jobs
box run --reason "why" [--box name|--new] [--size S|--gpu] [--env K=V] [--timeout d] -- <cmd...>   # box_run
box job <id> [--offset N --limit N]   # box_job: follow a job, or page through its log
box jobs [--box name]            # box_job without an id: jobs from /work/.box (*.pid, *.exit, *.log), newest first
box cancel <id>                  # box_cancel: kill the job's session (setsid), write .exit 130
box pull <id|box> <path> <dir>   # box_pull: incus file pull -r into a staging dir inside <dir>
box new [name] [--ttl 8h] [--size S|--gpu]  # CLI only: incus launch agent-base pc:<name> --project agents, with user.expires and the size
box rm <name>                    # CLI only
box ls                           # CLI only
box mcp                          # serve the tools on stdio: box_status, box_run, box_job (also lists jobs), box_cancel, box_pull
box watch [--state dir] <job>    # follow a job and push its end into the session's T3 thread (box_run starts it detached)
box join [--leave]               # register box mcp with claude/codex/antigravity (user scope) and install skills/box/SKILL.md
box ui [--url U]                 # the dashboard (docs/ui.md) in the browser: https://<host>/ of the pc remote
box app [--url U] [--wait]       # the same page in a window of its own (internal/desktop); for people, so not an MCP tool
```

`box status` reads `user.agent-box.mode` and the caps from the project, counts slots as `limits.instances` minus existing boxes, and says how many of each size fit (see Box sizes). `box join` uses `claude` and `codex`'s own CLIs to register the MCP server, and edits JSON files in place (preserving key order, other entries and BOMs, via `cmd/box/hook.go`'s ordered JSON helpers) only where there is no CLI: Claude Code's `settings.json` for `box hook`, and Antigravity's `config/mcp_config.json` (in `$GEMINI_HOME`, standalone `~/.gemini` and T3 Code's provider homes under `~/.t3/userdata/providers/antigravity/*`). Env names that look like secrets are refused, since boxes are shared.

`box run`:
1. Snapshots the worktree as a git commit without touching the user's index: a temporary `GIT_INDEX_FILE`, add everything not ignored, then `write-tree` and `commit-tree`. It sends a `git bundle` with `incus file push` and checks the commit out in `/work/<repo>`.
2. Runs the command with `incus exec ... -- bash -lc`, under `nohup` with output going to `/work/.box/<job>.log`, so a dropped connection loses nothing. `box job <id>` reattaches with `tail -f`.
3. Exits with the remote exit code, or 75 when the run can't go ahead and wasn't queued (`--no-queue`, a box paused mid-run, the PC out of reach), so callers can fall back to running locally.

By default it reuses one box per repo, which keeps caches and `node_modules` warm. `--new` creates a throwaway box. `--size` sets the size of a box the run launches (medium by default); when the repo's box exists in another size, the run uses a throwaway of the requested size and says so.

`box app` is a window around the page `box ui` opens, as `mur app` is in Murmur: the system's web view (WebView2 on Windows) through [glaze](https://github.com/crgimenes/glaze), which loads it at run time with purego, so there is no cgo and `box` still cross-compiles. glaze (and purego under it) is box's one dependency beyond `golang.org/x/sys`. The reason is the same as Murmur's app: a native window needs the platform's web view, and glaze is the cgo-free way to it that Murmur already runs on Windows; it raised `go.mod` to Go 1.27.1. Linux builds get the window only with `-tags desktop`, because purego makes the binary link glibc dynamically; macOS has none yet. When the PC doesn't answer, the window shows the page's "PC unreachable" screen from the copy of `internal/dash/static` built into `box`, served on loopback, whose `/api/state` checks the PC each time the page retries (every 10s) and sends the window there once it answers. Every 10s the window asks its document where it is; one that doesn't answer (an error page has no bindings), a 5xx, or another site sends the window back to the loopback page. In another site's document the init script cuts the bridge to the window before that page's own scripts run.

#### Failure digest

A finished `go test` or vitest run leads its result with a digest: `FAIL: 3 of 412 tests failed (go test)`, then each failed test with file:line and its first assertion or panic line, grouped by package or file, at most 3KiB (`internal/digest`). It goes first in box_run's and box_job's text, in `structuredContent.digest`, and in the pushed message. The command's exit code is its own, and the log is close to what the tool prints.

The report is machine-readable, never the human output parsed. The job's shell defines `go`, `vitest`, `npx`, `pnpm`, `yarn` and `npm` as functions (`digest.Wrappers`), passing through anything they don't handle. `go test` runs as `go test -json`, the events are kept in `/work/.box/<job>.gotest.json`, and jq (in the base image) prints them much as go test without `-json` does. The differences: `-json` can't tell a passing test's `fmt.Println` from its `t.Log`, so both are dropped; a failed subtest's lines come before its parent's, unindented; build errors go to stdout. A test holds back at most its first 200 and last 100 lines, so a chatty test costs linear time. Vitest gets `--reporter=json --outputFile.json=<job>.vitest.json` (and `.vitest.<n>.json` for later runs in the same job, merged by `Script`) beside its default reporter, or beside the reporters the command names. Only the shell running the command has the functions, so a script that calls `go test` itself runs the real one. Some shapes run untouched and get no digest: benchmarks (a passing benchmark's result is its output), vitest after `--` or with `reporters` or `outputFile` in its config (the flags would replace them), an `npm test` or `npm run` script that isn't plain `vitest` or targets multiple workspaces (single-directory `-w`/`--prefix` is supported), a box without jq.

The laptop builds the digest because that half is plain Go with tests, and it needs no new binary in the box. When the follow sees the job's exit, it prints the exit line, then runs jq over the reports in the same exec for at most 10 seconds and prints the result on stderr, so a job's end costs no extra round trip and the digest can't hold the result back (a follow cut off first just has no digest). jq cuts a Go report down to the failures, package ends and counts per package first, then the first lines of what failed, then an end mark, within 1MiB; a cut loses only output lines, and the digest says so. `digest.Parse` writes the digest. It is recorded with the job's end, so `box_job` still has it once the box is gone. A report that can't be read costs only the digest.

#### Pushing results to the agent

Claude Code and Codex can't background an MCP call, so an agent that waits on `box_run` sits idle (Tyler, 2026-11-24: "blocking for 10mins is crazy"). Instead `box_run` waits 30 seconds, counted from the command's start, and a job still running comes back as `state: running` (`exitCode: null`) with `push: true|false` and its ID. `box_run` takes no `box` or `wait`; naming a box is for the CLI. It takes `push: false`, which subagents pass.

**The rule: a duplicate notice is fine, a lost one is not.** Every choice below leans that way. A duplicate costs the agent a line to skim; a lost result leaves it waiting on a job that ended.

- **`push: true`** means box knows a T3 thread for the session (`T3CODE_THREAD_ID`, or `_meta.threadId` on the call, which is where Codex's bare-environment MCP servers get it) and could start a watcher. box starts `box watch --state <dir> <job>` detached (Windows: its own process group and a hidden console, breaking away from the MCP server's job object). Codex starts its MCP servers in a job object that refuses breakaway (access denied, 2026-11-25); the watcher then starts inside it and lives as long as the MCP server, which Codex keeps for its session. If it dies with the server, its leases expire (90 seconds, or 2 minutes mid-send) and the safety net restarts it on the thread's next `box_*` call; the run's result says the push lasts only as long as the MCP server, and to call `box_job` if the session restarts first. The watcher follows the job and, when it ends, runs `t3 thread send <thread> -` with the message on stdin. T3's CLI is at `T3CODE_CLI_PATH`, else `~/.t3/bin/t3.cmd`; the send goes behind the `Pusher` interface. A busy thread gets the message as its next turn. Every command the watcher runs (`t3.cmd`, incus) is started with a hidden window.
- **`push: false`** (no T3 thread, no `t3` CLI, `push: false` asked for, or the watcher couldn't start): the agent calls `box_job`, which waits up to 10 minutes.
- **The message** is `box: job <id> ended, exit N, after 6m12s. From box, not your user.`, the run's reason, `<command>  in  <worktree>`, a test run's failure digest (below), the last 20 lines, and where to read the full log and pull artifacts. T3 keeps what it is sent, so the reason, command and tail go through the same secret masking boxd's history uses (`internal/mask`, shared). A throwaway box and its log are kept 30 minutes after the job ends, not deleted: the watcher and `box_job` set `user.expires` to now plus 30 minutes and the reaper deletes it, so `box_pull` and the full log still work after the push, and the message says so. The end report to boxd is unchanged. A job paused mid-run is pushed once ("paused: ... resumes if they switch back within 15 minutes (4 hours once its memory is moved to swap), else it is lost ... box_cancel this job"), then watched on. T3 delivers a push when the agent's turn ends, so it can arrive after the job resumed: the message says the end push follows, and to check `box_job` before cancelling (#96). A command that itself exits 75 is a `done` result, and its message says so; "exit 75, run it locally" applies only to `state: refused`, a paused push that the agent can't wait for, and a `lost` push.
- **Lost is confirmed.** A broken follow (a dropped connection, the PC out of reach) is retried with backoff, and nothing is pushed while the PC can't be reached. The watcher pushes `lost, exit 75` only after it looks: the box is gone or stopped, or `box job`'s state for the job is `died` (its process is dead and left no `.exit`). The pause probe also notices a deleted box and ends the follow.
- **Cancelled is quiet.** `box_cancel` records `.notified` locally, and `cancelScript` writes a `.cancelled` mark on the box before the exit file, so a cancel from anywhere (`box cancel` on another machine) is skipped by the watcher too.
- **State** is in `%LOCALAPPDATA%\agent-box\jobs` on the laptop, per job. `.json` is the record: the recipient thread, reason, command, worktree. `.watch` and `.sending` are leases: `<token> <expiry>`, made with an exclusive create, taken over only after they expire, renewed by their holder every 20 s (the watch lease lasts 90 s, the send lease 2 minutes). So two watchers can't run, and a restarted one can't send alongside one mid-send. `.ended` holds the job's end (exit code or lost, how long, the tail) and is written before anything is sent. `.notified` means the end reached the agent. Markers and temporary files are created exclusively under unique names (a hard link for markers, so they are never seen empty), filesystem errors are told apart from "already there", and orphaned temporary files older than an hour are deleted. Records older than 7 days are deleted.
- **Delivery.** The watcher makes `.notified` only after `t3 thread send` succeeded, with up to four tries. A send that fails, or a watcher that dies mid-send, leaves `.ended` without `.notified`: the end is still owed. `box_job` always returns the full result, tail included, and then makes `.notified` so the watcher stays quiet; so does the CLI's `box job`, which agents run from a shell and which keeps a throwaway 30 minutes, as `box mcp` does (#78). If the watcher and `box_job` race, the agent may get it twice; it never gets it zero times.
- **Safety net.** Every `box_*` call first looks at the records for this session's thread. For each job without `.notified`: if it has ended, the result starts with `finished since you last looked: <job> exit N`, and keeps starting with it until `.notified` exists; if it has no live watcher (a laptop sleep or reboot kills them) or, once ended, nobody is sending it, a watcher is started to follow it or retry the send. Only the recipient thread's session sees the line.

Known limits. Subagents share their parent's thread, so a push wakes the parent: the skill tells subagents to pass `push: false` and call `box_job`. T3 may hold a pushed turn queued behind a running turn; the safety net line covers that. Outside T3 there is no push.

### 2. Tray app (Windows): mode switch

| Mode | Per box | Project memory cap | Notes |
|---|---|---|---|
| My PC | paused, then pushed to swap; a GPU box is stopped (see The GPU box) | 12GiB | Boxes still frozen after 15 minutes are stopped to free RAM; 4 hours once a reclaim moved them to swap (Memory, below). A "Release memory" item runs `wsl --terminate agents`. |
| Shared | `limits.cpu` = the size's Shared CPUs (1/2/4), `limits.cpu.priority=0` | 12GiB | Resumes paused boxes. |
| Full | `limits.cpu` = the size's Full CPUs (2/4/8), `limits.cpu.priority=10` | 24GiB | Resumes paused boxes. |

- `limits.cpu=N` is the real cap: the box can use at most N CPUs. `limits.cpu.allowance` is only a weight between Linux processes, so it does nothing against Windows. A box's memory stays as it was launched in every mode; the project's memory cap follows the mode (Memory, below).
- **Every tick** the tray reads each instance's config from `incus list --format json` and sets only the keys that differ, so a limit an agent changed is put back, with no extra calls when nothing changed. In My PC it pauses any running instance on every tick, which also catches an agent resuming one.
- Game detection was removed on 2026-11-25 (Tyler): the owner switches modes by hand; automatic switching may come later.
- It uses an admin client cert, which agents don't have. The mode is stored in the `agents` project config as `user.agent-box.mode`, so `box` can read it. A mode check in `box` is advisory: an agent can ignore it. The tray's per-tick enforcement is what holds the limits.
- The tray also holds a Windows power request while any instance is running, so the PC doesn't sleep in the middle of a job.
- **Logon and logging.** On 2026-11-23 the tray exited with code 1 at logon and nothing recorded why, so no mode was enforced. Now it logs to `%LOCALAPPDATA%\agent-box\boxtray.log` (start, every exit path, mode changes; capped at 1 MB by dropping the older half). If adding the notification icon fails, the tray retries every 2 s for 2 min while the mode loop keeps running, and it adds the icon again on `TaskbarCreated` (Explorer restart). The `agent-box-tray` task's restart setting doesn't restart it after an error exit (#97, tried 2026-11-25); the headless enforcer covers a tray that died.
- **Headless enforcer (2026-11-24).** The tray only runs while Tyler is logged on, and it was the only thing enforcing the mode. After the PC rebooted unattended (it crashes and restarts), nothing enforced for 20+ hours: `limits.memory` stayed at 12GiB while the mode key said `full`, so large boxes couldn't launch. `boxtray.exe --headless` fixes that: the same `mode.Manager` loop with Full as the default mode, no UI and no Release memory. The `agent-box-enforcer` scheduled task starts it at boot, "run whether the user is logged on or not" (`S4U`, the same logon type as the keep-alive, so no password is stored; tried live: WSL works from it, in session 0). It logs to `boxtray-headless.log`, beside `boxtray.log`. Both update themselves (docs/releasing.md). To replace `boxtray.exe` some other way, stop the boxtray processes themselves, not the tasks: one that updated itself runs outside its task. Then start the enforcer task again.
  - **One enforcer at a time.** An interactive tray holds the named mutex `Global\agent-box-tray-active` for as long as it runs (it takes it first thing, so the overlap at logon is at most one headless tick). Each headless tick checks it; while it exists, the headless enforcer writes and calls nothing, holds no power request and drops its manager, so on logoff it starts from a clean slate and rewrites the mode label. A second headless one exits (`Global\agent-box-enforcer`); a tray never exits over the name, because the headless check opens it for an instant every tick and a tray that started then would exit with code 0 (no restart), leaving Full enforced all session. One tray per session is the `Local\agent-box-boxtray` mutex. If the check itself fails it counts as "no tray": two enforcers for a tick is harmless, none is not.
  - **At logon** the headless enforcer stands aside within a tick (5 s) and the tray applies the project's chosen mode. **At logoff** the tray's mutex goes with its process and the headless one is back within a tick, which also covers a tray that crashed (nothing restarts it before the next logon, #97). Both write the mode label, so for a tick or two after a hand-over the label may be the other one's; the label is read back once a minute (`ProjectRecheck`) and rewritten if it differs.
  - **Mode requests and the chosen mode (2026-11-24).** Both enforcers run the handshake in `internal/mode/request.go` (`Manager.Handshake`), described in docs/ui.md. Every tick the active one reads `user.agent-box.mode-request` (`{mode, at, by}`). A request older than 10 minutes, unreadable, or older than the last choice made here is dropped and cleared. Otherwise it is adopted, stored, saved to `boxtray.json` (tray only) and cleared, in that order, so a failure in between loses nothing. The pick the enforcers act on is the project key `user.agent-box.chosen` (`{mode, at}`), the single source of truth. A new enforcer reads it before its first apply; a click or an adopted request writes it. So the headless enforcer, which has no menu, takes Shared or My PC from the dashboard and keeps it, and the tray comes back to that pick, not to a stale `boxtray.json`. An empty project is seeded by the tray's saved pick; the headless enforcer's Full default is never stored. A click and a request race by time (`at`, from the same PC's clock). The cost is one more `incus project get` per tick for the request key.
  - **Heartbeat.** Whichever enforcer is active writes `user.agent-box.tray-seen` (RFC3339 UTC, at most every 30 s) and `user.agent-box.enforcer` (`tray` or `headless`), so the dashboard can say which is running. Neither is written while the distro is down or being released. When it starts enforcing, it also writes its build as `user.agent-box.tray-version` (docs/ui.md, `Version`).
  - **Why the tray task exited 1 at 23:36 on 2026-11-23.** That was the build from before the log existed. In it a failed `newTray` (the notification icon at logon, with Explorer not ready) was `os.Exit(1)`, with nothing logged. Task Scheduler history is off on the PC and the log did not exist, so this is read from the code, not from a record. The build with the icon retry and the log has not been through a logon yet.

#### Memory

The PC has 32 GB (Tyler, 2026-11-24: in Full, leave Windows about 6 GB). `.wslconfig` gives the WSL VM installed RAM minus 6 GB (26GB) and 24GB of swap. The distro itself (Incus, Tailscale, lxcfs) takes 1-2 GB, so boxes get 24GiB in Full. In Shared Tyler uses the PC, so boxes get the 12GiB they always had; My PC launches nothing, so it keeps 12GiB too. The budgets are `MemoryBudgets` in `internal/mode/size.go`.

- **The tray sets the cap.** Every tick it sets the project's `limits.memory` to the mode's budget, or to what existing boxes already hold if that is more (Incus refuses less), and only when the value differs. Going from Full to Shared with 20GiB of boxes leaves the cap at 20GiB; it tightens to 12GiB as those boxes go. Those boxes keep their RAM in Shared until then, which Tyler accepted for Full's sake. `box status` reads the cap, so its room follows the mode. `setup-host.sh` sets `limits.memory` only on a new project, so a re-run doesn't fight the tray.
- **My PC gets frozen boxes' RAM back.** A frozen box keeps its memory resident in the VM, so with a 26GB VM the owner could be left about 6 GB. After pausing a box for My PC, the tray pushes its memory to swap with cgroup v2 `memory.reclaim`, and WSL's free page reporting hands the RAM back to Windows. The code is `internal/mode/reclaim.go`.
  - **Every box may swap up to its own memory limit.** Incus writes `memory.swap.max=0` whenever it starts a container (seen on 2026-11-24: a restart reset it; `limits.cpu` changes, pause and resume didn't), and a restricted project refuses `limits.memory.swap` ("low-level config"). So on every tick, after pausing, GPU stops and thawing, the tray sets `memory.swap.max` on every running or frozen box to its `limits.memory` (own or from a profile), in one `wsl.exe` call that reports each box separately, writing only values that differ, as it does for `limits.cpu`. A box with no `limits.memory` is logged and left at 0. Reclaim is then a single `memory.reclaim` write with nothing to open or put back, so a reclaim that is cancelled, killed or raced leaves nothing to repair, and resuming a box depends on nothing but its CPU limits. The cost, accepted: a box that goes over its memory limit swaps (up to that limit again) before the OOM killer fires, so a runaway test gets slow before it fails.
  - The cgroup comes from the box's init PID (`/proc/<pid>/cgroup`) and must be exactly `lxc.payload.agents_<name>`. LXC adds a `-N` suffix when a stale directory is in the way, but `box` and `box-1` would then be ambiguous, so a suffixed cgroup is refused: its reclaim retries, and the 15-minute stop covers it. The script checks `frozen 1` in `cgroup.events` first. Reclaim works on a frozen cgroup, because the writing process does the work.
  - **Reclaim is best effort.** Each frozen box gets one `memory.reclaim` write per freeze and identity (name and init PID, so a recreated box starts fresh), in the background, all at once, bounded by `timeout 60` in the distro; every `wsl.exe` call the tray makes has a deadline. Only a write that never happened (WSL, PID or timeout failures) is retried, with backoff. What the box still holds afterwards is logged (`reclaimed <box>: <n>MiB left in RAM`) and picks how long it may stay frozen: 4 hours (`FrozenSwappedStop`) when this freeze's reclaim ran and left 256MiB or less, since a frozen box in swap costs Windows next to no RAM; 15 minutes otherwise (no reclaim yet, it left more, or there was no swap). The timer belongs to the instance (name and init PID), so a box recreated under the same name starts again at 15 minutes. Reclaim never stops a box itself; only that frozen limit does. A box is reclaimed only once this tick's swap batch has confirmed its `memory.swap.max` for that instance: Incus writes 0 when it starts a box, and on 2026-11-24 a box created while the tray was down was reclaimed before its swap was set, kept 2092MiB in RAM, and was stopped at 15 minutes. Waiting costs one tick (5 s). Ticks go on meanwhile, so pausing new boxes, that stop and the reaper aren't held up.
  - **Release memory** runs one `wsl --terminate` at a time (a second click while one runs is ignored). While it runs, the tick in progress is cancelled and waited for, queued and running reclaims are dropped and waited for, and a tick that starts calls no `wsl.exe -d agents`, which would start the distro again.
  - **Swap can run out; accepted.** A running box swaps only when it is over its own memory limit, which test runs rarely are, so running boxes filling the 24GB swap file is unlikely. If they do, a frozen box's reclaim is partial, it keeps the 15-minute limit, and that stop frees its RAM. No reservations or I/O limits.
  - Measured on 2026-11-24 with a box holding 3.26GB: it went to swap in 3.2s, and within 35s vmmem fell from 5.38 to 2.30 GB and Windows' free memory rose from 22.3 to 25.5 GB. The pages come back from swap when the box touches them after it resumes. GPU boxes are stopped, not frozen, so they aren't reclaimed.
- Swap is the default `swap.vhdx` in `%TEMP%` on C: (NVMe), grown only as it is used. 24GB holds every box's memory at once, unless running boxes over their limit are already using some.

## Boxes are compute, not storage

Boxes are throwaway compute. Push work to git before a box goes.

- **Expiry.** `box` stamps every box with `user.expires` (RFC3339 UTC): 24h from now while a job runs, 2h after the job finishes (so an idle box lives 2h). A job whose exit box never reads (no push, no `box_job`) would keep its 24h, so boxd, which sees every job end, sets the same 2h (30 minutes for a throwaway, as box gives it) once nothing else runs there, in a write Incus refuses if the box changed since boxd read it, and only over the job's own 24h (#53). A throwaway's room can then be taken for a launch; `box job` gives its end from boxd's history once the box is gone (#90).
- **Reaper.** On every tick, in every mode (My PC too, since deleting frees RAM and disk), the tray runs `incus delete --force` on each instance in project `agents` whose `user.expires` is in the past. An instance with no `user.expires`, or one that isn't RFC3339, is skipped (the bad value is reported once). A failed delete is retried next tick. The distro's `agent-box-reaper.timer` does the same every minute, so expired boxes go when nobody is logged on.
- **Disk caps.** Root disk 18/30/40GiB per box by size, set at launch. Project `limits.disk=210GiB` over all boxes and volumes, including the 30GiB cache.
- **Only `/cache` survives**, and it is a cache: it can be wiped at any time (Go, npm, Gradle, Android SDK, Robolectric, uv and browser downloads rebuild it).
- **Android SDK and Robolectric (lazy in `/cache`).** Baking the Android SDK into `agent-base` would bloat every non-Android box clone (~750 MiB). Instead, `default-profile.yaml` sets `ANDROID_HOME=/cache/android-sdk`, installs an `flock`-locked helper (`/usr/local/bin/agent-box-ensure-android-sdk`) and `sdkmanager` wrapper, and places a static Gradle `init.d` stub in `/cache/gradle/init.d/agent-box-android.gradle` that delegates to each box's own `/etc/agent-box/android-sdk.init.gradle` (restored by `profile.d` after a `/cache` wipe). On the first Android Gradle build (or `sdkmanager` call), the helper downloads `cmdline-tools`, `platform-tools`, API 34/35 platforms and build-tools with accepted licenses, stamped per spec under `.agent-box-stamps/`. The init script also sets `maven.repo.local=/cache/robolectric-m2` on `Test` tasks so Robolectric's `android-all` jars persist across boxes without sharing Gradle's `mavenLocal()` across repos.
